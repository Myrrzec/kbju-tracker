# AI-промпты

Промпты лежат в [`backend/app/services/prompts.py`](../backend/app/services/prompts.py).
Здесь — объяснение решений, чтобы было понятно, что и зачем менять при доработке.

## 1. Распознавание еды по фото

**Модель**: Claude (vision), вызов через `messages.create` с `tools` + `tool_choice`
принудительно указывающим на `return_food_analysis`.

**Почему tool use, а не "верни JSON в тексте"**: если просто попросить модель ответить
JSON-ом, она иногда добавляет пояснения до/после, форматирует markdown-блоком, или
слегка меняет структуру. Принудительный вызов инструмента (`tool_choice`) гарантирует
валидный JSON по заданной схеме — не нужно парсить текст регулярками/try-except вокруг
`json.loads`.

**Ключевые решения в промпте**:
- Явно попросили оценивать порцию **в граммах**, а не сразу КБЖУ на глаз — так модель
  сначала "рассуждает" о размере, что обычно повышает точность калорий.
- Поле `confidence` — важно для UX: в интерфейсе стоит визуально подсвечивать
  low-confidence позиции и явно предлагать пользователю поправить граммовку/название
  перед сохранением в дневник, а не молча доверять AI.
- Явный запрет "не выдумывай ингредиенты, которых не видно" — снижает галлюцинации
  (например, необоснованное добавление соуса/масла, которых не видно на фото).
- `notes` — место для оговорок ("на фото не видно способа готовки", "еда не найдена").
- **Важно**: изначально промпт слишком легко разрешал модели вернуть пустой `items`
  при любой неуверенности (плохой ракурс, освещение, частичная видимость блюда) —
  на практике это привело к тому, что бо́льшая часть реальных фото давала пустой
  результат вместо приблизительной оценки. Промпт переписан так, чтобы пустой список
  был редким крайним случаем (когда еды на фото вообще нет), а любая неуверенность
  из-за качества фото выражалась через `confidence: "low"` + объяснение в `notes`,
  а не через отказ. Если это качнётся в обратную сторону (AI начнёт слишком уверенно
  распознавать откровенно нечитаемые фото) — можно частично вернуть строгость.

**Что стоит протестировать и доработать по мере использования**:
- Сложные многосоставные блюда (плов, салаты с заправкой) — вероятно, точность будет
  ниже, стоит собрать реальные фото и посмотреть на реальные ошибки.
- Возможно, для типовых блюд стоит подмешивать в промпт справочник `FoodItem`
  (RAG-подход: сначала ищем похожие продукты в своей базе и просим модель
  скорректировать/выбрать, а не считать КБЖУ с нуля) — это повысит консистентность
  между одинаковыми блюдами на разных фото.

## 2. Персональные рекомендации

**Модель**: Claude (текст), обычный `messages.create` без tool use — здесь нужен
человекочитаемый текст, а не структура.

**Вход в промпт**:
- Краткая сводка профиля (пол, рост, вес, активность, цель)
- Целевые КБЖУ на день (посчитанные по формуле Миффлина-Сан Жеора,
  см. `app/services/nutrition_calc.py`)
- Сводка дневника по дням за последние N дней (по умолчанию 7)

**Ключевые решения в промпте**:
- Явный запрет на медицинские советы / диагнозы — приложение не заменяет врача,
  это важно и с точки зрения безопасности пользователя, и с юридической точки зрения.
- Требование интерпретировать цифры, а не пересказывать их — иначе рекомендации
  выглядят как "капитан очевидность" (модель просто повторяет то, что пользователь
  и так видит на графике).
- Явно попросили короткий формат без markdown-заголовков — рекомендации показываются
  в мобильном интерфейсе, длинный форматированный текст там плохо читается.

**Что стоит доработать**:
- Сейчас рекомендация генерируется по запросу пользователя (`POST /recommendations/generate`).
  Стоит подумать о cron-задаче, которая генерирует свежую рекомендацию раз в день/неделю
  автоматически.
- Можно добавить в промпт историю предыдущих рекомендаций, чтобы AI не повторял одно и
  то же каждый раз.
